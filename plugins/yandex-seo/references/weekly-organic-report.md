# Weekly Organic Report contract

The P2 workflow is a transport-free `yandex-seo` orchestration layer. Yandex Webmaster and Yandex Metrika remain the owners of service reads, credentials, API request semantics and volatile API facts. SEO consumes normalized evidence or user-provided normalized files and never calls Yandex APIs directly.

## Input envelope

Each service input for `build` is a JSON object with the same exact `period` and `comparison_period` plus the service-owned normalized payload.

Webmaster input preserves:

- `coverage`: `COMPLETE`, `PARTIAL` or `MISSING`;
- non-secret source identity such as site/host;
- query pagination/top-N/filter context;
- explicit limitations;
- `OBSERVED` evidence records;
- comparable query rows when available.

Metrika input preserves:

- `coverage`;
- non-secret counter identity;
- quality metadata such as `sampled`, `sample_share`, `sample_size`, `sample_space`, `data_lag`, `contains_sensitive_data` and `total_rows_rounded` when supplied;
- explicit limitations;
- `OBSERVED` evidence records;
- comparable page rows when available.

A missing source is not silently replaced by another source. The report marks it `MISSING` and carries a limitation. Materially inconsistent current/comparison periods are a hard error.

## Report contract

`seo-weekly-organic-report/v1` is the normative machine-readable report. It keeps project identity, exact periods, source coverage/metadata, deterministic movers/findings, limitations, evidence/provenance and delegated previews.

Empirical findings are `DERIVED` and reference existing evidence IDs. Missing comparison evidence does not become a zero. `METHODOLOGY` is not represented as observed API/ranking evidence.

`report_id` is derived from canonical semantic report content with `generated_at` excluded from the semantic preimage. Therefore the same semantic evidence can keep one logical report ID across rerenders, while immutable artifact-set collision rules prevent silent replacement by different generated bytes.

## Portable artifacts

`yandex-ai-artifact-manifest/v1` describes the managed artifact set. `artifact_set_id` is SHA-256 of the final canonical `report.json`; every managed file has a relative POSIX path, role, media type and SHA-256.

`report.html` is self-contained: inline CSS, minimal local-only JavaScript, embedded restrictive CSP, escaped source text, no CDN, remote fonts, analytics, remote media or network fetch. JSON is normative; HTML must not add findings absent from JSON.

Optional Mermaid/DOT files are exported only from structures already present in source evidence/artifacts:

- structural tree → Mermaid and DOT;
- semantic graph → Mermaid and DOT;
- clusters → Mermaid;
- internal-link plan → DOT.

No topology is synthesized merely to populate the artifact directory.

## Project Memory and safety

When `.yandex-ai/project.yaml` exists, the workflow may consume project identity and active `USER_STATED` facts as read-only context. It does not read hypotheses, decision history or stale baselines as authority, and memory never replaces fresh service evidence.

Delegated rows remain `PREVIEW-ONLY`. Neither a report, a prior decision nor Project Memory satisfies a P0 exact-preview approval or bulk acknowledgement. Any later consequential mutation is routed to its owning workflow and receives a new approval lifecycle.

## CLI

Credential-free demo:

```bash
python scripts/seo_weekly_report.py demo --output-root artifacts --generated-at 2026-09-06T12:30:00Z
```

Build from normalized evidence:

```bash
python scripts/seo_weekly_report.py build \
  --webmaster webmaster.json \
  --metrika metrika.json \
  --project-root . \
  --output-root artifacts
```

For projects without `.yandex-ai/project.yaml`, supply `--project-id` and `--project-name` together.
